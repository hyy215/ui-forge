# UI Forge D2C

读取线程中提供的设计与工程规则，并在原生线程 `cwd` 指定的目标目录中实现。当任务要求诊断或改进此工作流时，仅将示例应用作为证据，并把修改限制在相关配置、规则和 skill 内。

## 工作方式

实现前，结合原始图片、可用的设计结构和现有代码，识别各区域的组件、尺寸约束和状态行为。所有选择都应依据本次任务要求。仅凭导出节点的宽度不能证明布局应固定，缺少业务契约也不意味着常规 UI 行为应保持静态。默认由主 Agent 完成工作；复杂度确有需要时再制定计划，不要求额外的计划文件或固定报告格式。

当相互独立的工作能够节省时间，且本次任务允许委派时，按需使用已注册的 `d2c_design_analyst`、`d2c_patch_author`、`d2c_browser_renderer` 或 `d2c_reviewer` 角色；不必全部调用。每项委派都要包含相关设计、要求和明确的文件责任范围。

中间产物使用线程或当前应用上下文提供的 ui-forge 临时目录；命令可读取 `UI_FORGE_TEMP_DIR`。原始设计数据、截图、切片、差异图、验证报告和临时脚本都写入该目录。向工具传入该目录内的绝对输出路径，并为每个任务或子任务使用唯一子目录。委派工作时也要传递这一约定。最终源码、正式测试和应用实际使用的资源应放在目标工作区；交付时不要引用临时资源。不要自动移动或删除之前生成的文件。

运行与修改相匹配的工程检查，然后在真实浏览器中对比设计并验证交互与视口行为。检查组件选择、内边距与尺寸关系，以及每项行为产生的可观察结果。复用开发服务器和仍然有效的既有分析；修复后重新检查受影响区域。如果用户明确要求静态稿，只执行相应的视觉检查。

检查每项明确要求的行为、数据规模和视觉验收标准所对应的可观察结果。浏览器操作和测试应覆盖重要变化及恢复路径；仅打开页面、统计 DOM 节点或通过构建，不能证明拖拽、搜索、编辑、性能或视觉还原已经通过。检查大数据量时，使用不会进入交付数据的临时样本，实际执行所要求的滚动、搜索和更新，并记录测量环境与结果。如果设计给出了参考视口，先检查该尺寸，再检查其他必要视口。

交付时区分已验证、失败、未验证和受阻的要求，并提供可追溯的测试输出、截图或报告。没有证据时不要把要求标为通过。轮次完成、类型检查通过或构建成功只能证明对应事实，不能代表整项任务验收通过。说明解除阻塞所需的条件；用户仍可选择继续其他能够独立验证的工作。不要为了得到验收结果而扩大权限。

## 本地工具

- 确认本次任务所需工具可用后，使用包内配置的 Playwright MCP 进行浏览器检查。交互工具只能操作本次任务的本地预览和已授权范围。使用 `browser_evaluate` 读取元素边界、计算样式、字体和资源状态，不得用它修改页面、注入 CSS 或伪造截图状态。工具不可用时，报告尚未检查的项目；静态截图不能作为交互验证。
- 大型参考图难以检查时，先查看 `--help`，再按需使用 `scripts/slice_reference.py`。Python 3 和 Pillow 是图片脚本的可选依赖；缺少时应报告，不得未经授权自行安装。
- 仅在本次任务明确要求时使用严格像素比较；参见 [pixel-acceptance.md](references/pixel-acceptance.md)。

交付中应包含真实页面截图或预览链接。
