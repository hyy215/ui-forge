# D2C 工程要求

## 技术与可维护性

Agent 使用 React + TypeScript 编写页面，先检查并复用目标项目的现有结构和合适组件。根据项目与设计需要选择组件库；Ant Design 不是必选项。按照职责和实际复用关系拆分代码，保持组件接口与状态归属清晰；不要只为形式上的结构增加空目录层级或包装组件。

默认范围包括可交互视图、必要的本地 UI 状态和浏览器验证；交互与组件选择遵循本次任务的设计约束。只有用户明确要求静态稿时才省略交互。没有后端时，使用现有数据和用户输入驱动本地状态，保持组件接口清晰，不要新增业务框架、请求层或持久化。真实业务接入必须以用户明确提供的范围和契约为依据。

## 目录与文件组织

原生线程 `cwd` 指定的目标目录是应用源码范围。最终页面代码、正式测试和项目实际引用的资源都应保存在该目录内。截图、差异图、验收报告和临时脚本使用线程提供的 ui-forge 临时产物目录；命令可通过 `UI_FORGE_TEMP_DIR` 获取该目录。codex-client 包目录只提供配置和工具，不是目标应用目录。

优先遵循项目现有命名、导出约定和合理的目录结构。如果页面结构扁平、职责混杂或依赖倒置，应在本次实现范围内改善结构。不要用“沿用现有结构”为堆叠代码辩护，也不要把工作扩大为无关的全项目重构。

在应用入口、共享布局、页面和页面专属组件之间建立清晰边界：

- 应用入口负责初始化、全局配置和页面装配，不承载某个具体页面的完整内容。
- 共享布局负责跨页面复用的顶部栏、侧边栏容器和内容区；页面差异通过明确输入或组合表达。
- 每个独立页面使用自己的目录，其中包含入口、专属组件、展示数据和样式。
- 页面入口负责装配布局与区域；具有独立职责的完整区域应拆成页面专属组件，不要把多个完整区域及其实现都塞进入口文件。

将页面专属组件、hooks、类型和辅助函数就近放置。只被一个页面使用的内容不要放进全局共享目录。只有模块跨页面使用且职责稳定时才提升到共享目录；不要把业务专属逻辑放入通用 utils。类型默认与归属模块放在一起，只有在多处使用且确有独立职责时才单独建文件。

页面可以依赖共享模块，但共享模块不得依赖某个具体页面或其数据；避免循环依赖。共享导航类型和品牌配置属于共享布局或应用配置，不应混入某个页面的展示数据。页面之间不得通过导入彼此的内部文件来复用代码。

按照实际职责命名目录和文件，页面入口命名保持一致。`data.ts`、`styles.css` 等通用名称可以在归属清晰的页面目录中使用；不要在源码根目录用这类文件混合多个页面的内容。

根据职责、依赖和变更范围拆分代码，而不是采用僵硬的文件长度限制。不要仅为了增加层级而添加空目录、只做转发的文件，或没有布局与语义职责的包装组件。没有实际需要时，不要预先创建 hooks、services、store 或 utils 目录。

## 组件与 Hooks

组件用于表达界面并组合交互。将复杂状态逻辑、订阅或可复用行为提取到自定义 hook；纯数据转换、校验和业务计算使用普通函数。不要仅为缩短文件而机械拆分组件或 hook。

组件接口应表达业务意图；避免大量彼此关联的布尔参数，也不要通过接口暴露内部实现。互斥状态优先使用明确的状态类型。

在组件或自定义 hook 的顶层调用 hooks，提供完整依赖，不要通过禁用 lint 规则逃避依赖问题。effect 用于与外部系统同步；派生数据在渲染期间计算，用户触发的逻辑放在事件处理函数中。清理订阅、定时器和异步请求，并处理过期结果，避免卸载后继续产生副作用或旧请求覆盖新结果。

仅在有明确性能或引用稳定性需求时使用 `useMemo`、`useCallback` 和 `memo`。不要默认包装所有值、函数和组件，也不要依赖缓存保证业务正确性。

## 状态管理

每项状态保持单一事实来源，不要存储能够从现有数据推导出的值。将状态放在最近的共同使用层级，并区分服务端数据、表单状态和临时 UI 状态。只有存在真实的跨区域共享需求时才引入全局状态。

使用表单或数据请求库时，采用库自身的状态管理机制，不要维护一份需要手动同步的重复状态。以不可变方式更新状态，并使用稳定的业务标识作为列表 key。

## 数据边界

展示数据由其所属页面或共享模块管理；页面专属数据就近放置，不要集中到通用的跨页面数据文件中。只使用设计、项目约束或实际读取明确提供的数据；用户输入产生的本地编辑值应单独维护。缺少信息时进行说明，不要编造业务数据或规则。不要把展开、选中、编辑草稿等 UI 状态误认为被禁止新增的业务数据。只有用户明确要求且提供了契约时才实现后端接入。

区分设计原始文字、明确提供的数据和用于还原图形的视觉比例，并记录必要的来源说明。从图形尺寸推断的比例只用于视觉还原，不得作为真实业务数据展示；来源无法确认时应明确说明。

对于含义不同的资源或配置，使用具名字段，不要用数组位置编码含义。明确声明初始选中、展开和编辑状态，后续变化通过稳定标识管理，不要依赖文案或行号。

为组件输入、业务数据和 API 响应定义类型。不要用 `any` 或类型断言掩盖契约问题。在集成边界校验和转换外部数据，不要把响应字段适配散落在渲染代码中。

分离数据访问与展示，使当前数据源能够被后续指定的 API 替换。不要为尚不存在的需求搭建通用请求框架。

## 样式与依赖

限制样式作用域，共享视觉规则优先使用项目 token 或现有样式。根据本次任务的设计约束选择和定制组件。对于组件库组件，优先使用公开定制接口，必要时在组件根类名下使用局部样式。避免无作用域的全局覆盖、层层叠加的优先级补丁，以及依赖深层内部 DOM、`nth-child` 或动态哈希类名的脆弱选择器。

全局样式只应包含字体、基础重置和全局设计变量。共享布局、共享组件和页面样式应与各自所属模块组织在一起。一个页面不得依赖另一个页面的样式才能完整显示。合并颜色、间距等重复设计值；使用组件库时，保持 CSS 与组件库主题中的对应值一致。

组件内部父子元素的尺寸，以及图表刻度、网格和绘图区，应共享明确的尺寸基准，不要在 TSX 与 CSS 中分别维护彼此依赖的数值。遵守 AGENTS.md 中关于容器和资源尺寸的约束；不要用裁切或额外覆盖隐藏尺寸冲突。

每个组件在各断点下保持一套清晰的样式规则，避免重复声明和冲突覆盖。根据设计关系调整容器尺寸和内容，不要机械固定参考图中测得的宽度。如果没有提供断点方案，不要新增页面或改变信息顺序；在本次任务的设计约束下报告验证视口和必要假设。

优先使用现有依赖和能力。新增依赖必须有明确收益，并考虑包体积、兼容性和维护成本；避免引入职责重复的库。

## 交付与验证

变更应聚焦本次任务要求，移除本次修改产生的废弃代码和临时调试内容，不包含无关重构。注释应解释必要的业务约束或实现原因，而不是复述代码。交付时说明关键假设和已知限制。

手写 TSX、TypeScript 和 CSS 保持可读的缩进与换行，不把组件或整份样式压缩成单行。优先使用目标项目已有格式化命令或已安装的格式化工具，完成后检查本次改动；缺少工具时按项目约定整理，不为格式化擅自安装依赖或启动额外模型任务。

检查页面目录归属是否清晰、入口文件是否避免包含完整区域实现、共享模块是否不依赖页面，以及数据与样式是否没有跨页面混用。目录结构应直接反映实际职责。

完成与变更范围相匹配的类型、构建及相关检查，并在真实浏览器中进行视觉和本地交互验证；合并重复检查。检查组件选择、尺寸与 padding 关系、资源变形、内容溢出、遮挡和数据来源。验证主要已实现交互的可观察结果；对于已授权的上传或下载，检查内容或生成文件。不要触发未经授权的外部副作用。使用文件位置或截图证据支撑结论，并明确标记未验证项。

使用对应的规则测试或真实浏览器操作证明明确列出的行为与容量要求。不要根据页面加载、少量点击、DOM 数量或构建成功推断其他要求已经通过。容量验收使用与交付数据隔离的临时样本，实际验证所要求的滚动、搜索、编辑和顺序更新。报告观察到的耗时或卡顿及其环境；不要把一次本地运行描述为跨设备保证。

将复杂交互的操作与结果断言保留为可重复运行的测试或临时脚本。当前连接器没有拖拽等操作入口时，检查项目已有的浏览器自动化能力是否可完成真实操作；不要通过直接修改应用状态代替交互。性能记录包含样本量、视口、浏览器、操作与测量起止口径，只有功能操作结果时标为功能检查，不宣称性能通过。

按本次实际实现选择关键路径及其恢复分支，不要求每个页面执行同一套用例：

- 表单或可编辑表格：检查确认后实际值、取消后恢复值；存在异步提交时，用可控的本地失败验证错误反馈和草稿保留，再检查重试。不得把本地修改说成后端保存成功。
- 搜索与树形导航：检查命中对象、清空后的恢复、无结果，以及需要展示的祖先展开路径；不只断言输入框或搜索按钮存在。
- 拖拽或排序：记录真实操作前后的稳定标识顺序；有层级时覆盖规则明确禁止的移动，不能通过直接改状态冒充拖拽成功。
- 派生数值：使用已有业务规则或用户明确的契约，断言输入变化与明细、合计的一致性；规则不明时标记缺口，不编造算法。
- 主要操作入口：验证点击后可观察的内容、状态或授权文件结果；空处理器、只有提示而没有结果的按钮不能记为通过。

验证记录按具体要求逐项关联“前置状态、操作或命令、预期、实测、环境、证据”。截图用于外观，操作断言用于行为，测量输出用于性能；不同证据不能相互替代。详细记录使用当前任务产物目录，不把测试数据混入最终页面。修复后只重跑受影响项；相关源码变化但未复验时，保留旧证据并将当前结论标为未验证。

优先测试关键业务规则和容易回归的行为，断言可观察结果，避免测试与组件内部实现耦合。对于简单样式修改，不要编写机械重复实现的测试。

启动并保持一个可访问的预览服务器，尽量复用已有服务。交付用户可直接打开和操作的页面链接，并附上真实页面截图。报告工程检查、视觉验证、交互验证结果和未解决差异，区分已实现的本地交互与尚未接入的业务能力。如果无法提供预览，说明原因；不要用文字总结替代预览结果。
