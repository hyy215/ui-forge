# 提交与 Draft PR 交付

默认将本次任务通过以 `main` 为基准的 Draft PR 交付，只有用户明确指定时才采用其他方式。一个 PR 始终只保留一个 commit：本地可以多次提交，每次推送前将本次任务的提交合并为一个。先完成本地准备，再请用户确认推送。

## 检查本次变更

- 遵循适用的 `AGENTS.md`，查看本次任务已有提交、暂存区、未暂存及未跟踪文件，确定提交范围。用户指定范围优先；没有指定时优先采用暂存内容，并核对它与本次任务一致。无关修改不纳入提交，范围不清时先澄清。
- 阅读本次完整 diff 和必要的关联实现，检查需求是否实现、明显错误、回归和缺失验证。提交前检查差异格式及密钥、私有资产、构建产物、本地状态等误入内容；不能等上传后再检查敏感内容。
- 全量验证由 GitHub CI（GitHub Actions）执行；本地仅按需验证，复用仍有效的结果，不重复运行整套检查。
- 在用户已授权范围内修复发现的问题，修复后核对增量及受影响部分；不把提交检查扩展为无关重构或反复全仓库审核。需要用户决策的问题集中说明。
- 仅要求审核时，到检查结果为止，不暂存、改写提交或推送。没有变更时不创建空 commit 或空 PR。

## 整理为一个 commit

- 日常修改无需新建分支。交付时使用本次任务的 `codex/<task-name>` 分支，可以复用尚未完成的任务分支；默认分支和其他任务的分支不用于创建交付 commit。
- 刷新目标分支，确认本次提交范围及分叉点。无需为了创建 Draft PR 强制把任务分支更新到最新 `main`；合并前满足 GitHub 的更新与检查要求。
- 将本次任务已有提交和选定的未提交修改整理为一个 commit，保留无关内容。仅改写本次任务的提交；无法安全分离时停止并说明。整理后核对文件差异与已检查内容一致，并确认从目标分支与 HEAD 的共同祖先到 HEAD 恰好只有一个 commit。
- 提交信息简明说明实际变更，优先使用用户给定内容；修改方案与验证结果写入 PR 正文，不要求 commit message 带 PR 链接。正常执行 Git hooks。

## 推送前确认

- 本地 commit 准备好后，展示提交范围、目标仓库与分支、最终 commit、PR 标题与正文，以及本地验证结果和已知问题，再请用户确认推送。默认使用 Draft PR，不要求用户每次重新选择交付方式。
- 用户已对当前这份具体交付内容明确确认时不重复询问。确认后若提交内容、目标或推送方式发生变化，更新说明并重新确认；笼统的“提交”不代替本次推送确认。
- 更新已有 PR 也保持一个 commit。若需改写已推送的提交，在确认中明确说明，并记录刚核对的远端 SHA；只对本次任务分支使用绑定该 SHA 的 `--force-with-lease`。远端被他人更新或 lease 不匹配时停止，重新核对后再确认。

## 推送与 GitHub CI

- 确认后推送任务分支并创建或更新 Draft PR。既有 PR 已进入人工审阅时，先说明改写提交会使审阅依据变化，再取得确认。不自动将 Draft 转为正式审阅，不合并或关闭 PR。
- 核对本地 HEAD、远端任务分支和 PR Head SHA 一致，确认 PR 只包含一个 commit，返回真实 PR 链接。
- 推送后查看最终提交对应的 GitHub CI 结果，不在本地重复运行整套检查。未完成、失败或无法获取时如实报告；“已创建 Draft PR”和“GitHub CI 已通过”分别说明。检查通过前保持 Draft，不把未运行的检查视为通过。
- GitHub CI 失败时定位原因，在本次任务已授权范围内修复，仍按单 commit 整理并在再次推送前确认；外部权限、服务故障或范围外变更需要用户处理时明确说明。
- 用户指定直接推送 `main` 等其他方式时，仍确认具体内容并遵守远端保护，只允许非强制推送。不绕过保护，不强推 `main`，失败后不擅自改走其他交付方式。
