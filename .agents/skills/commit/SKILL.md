# 提交质量门禁

审核并提交一个精确、冻结的候选快照。用户要求提交即授权在门禁通过后创建一个本地 commit；当适用的仓库 `AGENTS.md` 明确把 PR 规定为默认交付方式时，已获授权的代码变更任务还授权在门禁通过后执行本技能定义的受限 push、Draft PR 创建、一次 commit message 最终化和远端校验。除此之外禁止 push、amend、发布、安装依赖、删除文件、合并 PR 或扩大范围。

本流程必须有界：对同一候选快照只执行一次完整发现式审核。修复后的复审只验证问题台账、修复增量、受影响接口和既定门禁，不得重新对未变化代码进行开放式找茬。

## 1. 确定范围并冻结快照

1. 从仓库根目录工作。枚举并完整阅读根目录及候选文件祖先目录中的所有 `AGENTS.md`；阅读根 `README.md` 和与变更直接相关的设计文档。不得只依赖会话注入或旧摘要。
2. 在任何 stage 操作前运行 `git status --short`，分别检查 `git diff --cached`、`git diff`，并单独枚举、打开所有 untracked files。
3. 用户指定范围时严格遵守；否则 index 非空时以 staged changes 为候选，index 为空时选择与当前任务一致的内聚变更集。多个无法安全拆分的无关变更属于范围阻断项。
4. 记录候选路径和明确排除的 modified/untracked 路径。禁止意外 stage。
5. 记录初始快照标识：候选路径清单、`git status --short`、cached/unstaged 完整 Patch 的内容哈希，以及每个 untracked 文件的内容哈希。统计摘要不能代替内容哈希。后续任何内容变化都视为新快照，必须记录变化来源。

## 2. 一次性建立完整清单

在首轮发现式审核中一次性完成以下工作，不要发现一个问题就立即停止剩余检查：

- 对 cached 和 unstaged 变更运行 `git diff --stat`、`--numstat`、`--summary`、`--check`。
- 分块完整阅读 Patch，避免工具输出截断；打开每个 untracked 文件，二进制文件检查类型、大小和来源。
- 对每个文件或内聚分组记录：改了什么、行为原因、重要接口/数据流/依赖、对应测试/文档、是否属于本次提交。
- 覆盖新增、修改、删除、重命名、生成文件、依赖、lockfile、fixture、配置、测试和文档；与 `git status --short` 逐项对账。

变更规模大时先按 package 或能力边界分组，再逐组完成同一检查清单。规模本身不是阻断项，但无法完整读取或无法确认范围是阻断项。

## 3. 前置运行全部确定性门禁

在语义审核结论前确定并运行完整验证矩阵，避免后续零散增加检查项：

1. **依赖完整性**：存在 lockfile 或依赖变更时运行项目包管理器的完整性命令；npm workspace 至少运行 `npm ls --all`。缺依赖、无效依赖树或 lockfile 不一致属于阻断项。禁止自动安装，等待用户明确授权。
2. **机械检查**：运行项目已有的 format、lint、typecheck、Schema/代码生成一致性检查。
3. **测试**：先运行与行为变化直接相关的测试，再运行仓库规则要求的完整测试。
4. **构建**：修改公共协议、构建配置、入口、依赖或跨 workspace 引用时运行完整 check 与 build。
5. **Patch 卫生**：运行 `git diff --check`，扫描候选路径和内容中的密钥、私有资产、构建产物、本地状态及禁止目录。

开始语义审核前先列出验证矩阵。首轮结束后不得仅因“想到新的通用命令”而追加门禁；只有 Patch 中确有证据表明某项专用验证此前无法预见时才能补充，并在问题台账中说明原因。

记录每条命令、退出状态和关键结果。未运行、不可用或仅凭推断的检查不得宣称通过。

## 4. 一次性语义审核

以生产标准完整审核冻结快照，优先检查正确性、回归、安全、数据丢失、并发、错误处理、兼容性、缺失测试和误导性文档。发现问题时引用准确路径和行号，但继续完成其余既定检查后再统一报告。

将所有适用 `AGENTS.md` 要求映射到候选文件、Patch 证据或验证命令。嵌套规则优先；冲突、失效或无法同时满足的规则属于阻断项。候选中包含 `AGENTS.md` 时，还要审核规则本身，并按最终规则重新核对其作用域内候选文件。

对本仓库至少核对：

- package/应用边界与 shared-protocol 通信归属；
- Zod 运行时校验、外部数据不可信边界与结构化工具输入输出；
- TypeScript strict、无 `any` 逃逸、NodeNext `.js` 导入和 Project References；
- 文件级及公共声明/类成员文档注释；
- Patch 审批哈希、文件版本、事件 `seq`、Token/Event 分流、权限、预算、修复轮次、路径和符号链接安全；
- Schema 拒绝、权限拒绝、取消、预算终止等适用分支测试；
- 实现与文档一致，成果声明有可重复证据；
- 无密钥、私有资产、构建产物、本地运行数据和 `references/` 文件。

公共协议变化必须同时检查 Server、Webview、Extension 和相关能力包。

## 5. 无用代码与公共提取

使用 `rg`、类型检查和邻近实现检查未使用 import、变量、export、组件、函数、类型、依赖、配置、feature flag、兼容层、过期注释、陈旧测试和删除残留。区分公共 API/框架入口与真实不可达代码。

比较重复的 Schema、协议类型、消息构造器、校验逻辑、hook、组件、常量和测试 helper。只有职责明确、语义一致、已有实际复用且目标边界正确时才要求提取；表面相似或假设性复用不构成阻断。

确认的无用代码、契约分叉或必须提取的重复属于阻断项；可选清理单列为非阻断建议。

## 6. 建立固定问题台账

首轮发现式审核完成后一次性建立问题台账。每项包含：

- 稳定编号（如 `B1`、`B2`、`N1`）；
- 严重程度与 blocking/non-blocking；
- 精确证据和受影响行为；
- 发现来源（确定性门禁、仓库规则或语义审核）；
- 允许的安全修复路径；
- 状态（open/resolved/accepted）。

首轮报告后冻结台账，不得在同一快照上重复启动新的开放式审核。门禁失败时禁止 stage 和 commit，也不得在本 skill 内静默修复；使用中文给出完整 diff 概述、规则核对、验证证据、无用代码/提取结论和全部阻断项，等待用户明确授权修改。

## 7. 有界修复复审

用户授权修复后，将修改前快照作为基线，并在修复完成时记录新快照。复审范围严格限制为：

1. 逐项验证台账中的 open blocker 已解决且未被绕过；
2. 完整阅读修复增量；
3. 检查修复直接影响的调用方、公共协议、配置和数据流；
4. 重跑原验证矩阵及修复明确要求的专用测试；
5. 重新运行 Patch 卫生和敏感信息扫描。

不得重新审核与修复无关且内容未变化的代码，也不得把新的风格偏好、可选重构或此前遗漏的非阻断建议升级为 blocker。

复审若发现新问题，必须分类：

- **修复引入或修复直接暴露**：加入台账，说明因果证据并阻断；
- **确定性门禁新失败**：加入台账并阻断；
- **与修复无关的迟到发现**：明确标记为首轮漏审，停止本次自动循环并请求用户决定，禁止继续边审边改；
- **非阻断建议**：记录但不得阻止提交。

一次 `$commit` 工作流最多执行一次完整发现式审核和一次授权修复复审。复审仍有 blocker 时结束当前工作流；后续修复必须由用户明确发起，不能自动无限循环。

## 8. 提交判定

以下任一情况使门禁失败：

- 台账仍有 open blocker；
- 正确性、回归、安全、数据、兼容性或仓库规则问题未解决；
- 确认存在无保留依据的无用代码或必须公共提取的契约重复；
- 依赖完整性、必需 test/check/build 或 Patch 卫生失败或无法运行；
- 候选范围含糊、遗漏或包含无关内容；
- 适用规则未完整发现、读取和核对；
- 当前 Patch 不匹配已审核的新快照。

没有 blocker 时明确声明门禁通过；非阻断建议单列，不掩盖结果。

## 9. 创建候选 commit

1. 只 stage 已审核候选路径，保留排除的工作区修改。
2. 运行 `git diff --cached --check`、`git diff --cached --stat`，将 staged 路径和 Patch 与审核快照逐项对账。仅 stage 操作造成表示变化而内容相同时无需重新发现式审核；内容变化则门禁失败。
3. 最后扫描 staged Patch 和路径中的密钥及禁止产物。
4. 使用用户提供的 commit message；否则根据主要变更生成简洁 subject，不虚构 issue ID 或成果。仓库要求 PR 交付时，候选正文先记录真实的“修改方案”，并使用 `PR: pending` 占位；不得预估或猜测 PR 编号。
5. 使用 `git commit` 创建一个本地候选 commit；禁止 `--no-verify`。本步骤本身不执行 amend 或 push。
6. 记录候选 commit hash、tree hash、subject、提交分组、验证矩阵结果、问题台账最终状态和剩余工作区变更，为 PR 最终化建立不变量。

commit 失败时报告原始错误并保持工作区完整。

## 10. 自动交付 Draft PR

仅当适用的仓库规则明确要求 PR 交付时执行本节；否则在本地候选 commit 创建后结束。

1. 确认当前分支不是默认分支、分支名符合仓库约定、候选 commit 相对最新 `origin/main` 恰好领先一个 commit，且工作区与 index 没有本技能引入的未提交内容。任一条件不满足都停止，不通过重写无关历史来凑成单提交。
2. 将当前任务分支推送到 `origin`。禁止推送默认分支、使用普通 `--force` 或绕过远端保护。
3. 使用可用的 GitHub 连接器或已授权 API 创建以 `main` 为基准的 Draft PR。PR 标题与候选 subject 一致；正文包含目标、修改方案、验证证据、风险和未完成事项。记录服务端返回的 PR 编号与规范 URL，不从分支名推断 URL。
4. 使用规范 PR URL 生成最终 commit message。正文必须包含“修改方案：”和独占一行的 `PR: <canonical-url>`；修改方案至少包含一条真实、非空的列表项。
5. 使用 `git commit --amend` 仅替换候选 commit message。amend 前后 tree hash、候选路径内容和排除的工作区状态必须一致；任何内容变化都使门禁失败。
6. 在 PR 尚未开始人工审阅且远端仍指向本技能刚推送的候选 commit 时，只执行一次 `git push --force-with-lease`。lease 不匹配、出现新 review 或远端分支被他人更新时立即停止，禁止覆盖。
7. 校验本地 `HEAD`、远端任务分支和 PR Head SHA 完全一致，并确认 PR 仍为 Draft。等待或读取 `check` 与 `commit-metadata` 等必需检查的状态；检查失败时保持 Draft 并报告失败证据，不自动修复或合并。
8. PR 创建后任一步骤失败时，报告候选/最终 commit SHA、PR URL、远端状态和可恢复边界；不得要求用户执行未说明风险的历史重写，也不得把不一致状态宣称为已交付。

## 11. 交付报告

报告最终 commit hash 与 subject、提交分组、验证矩阵、问题台账最终状态、剩余工作区修改，以及 Draft PR 的可点击完整链接和检查状态。只有本地、远端和 PR Head SHA 一致时才声明 PR 已交付；本技能永不自动合并或关闭 PR。
