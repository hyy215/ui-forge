# 代码修改前置计划

把计划确认作为代码修改的授权边界。用户要求实现、修复、重构或其他会改动代码相关项目文件的任务时，必须先让用户看到计划并确认；不能把最初的修改请求本身视为对计划的确认。

## 确认前

只进行制定可靠计划所必需的只读工作，例如：

- 阅读适用的仓库说明、约束、源码和测试；
- 检查 Git 状态与现有 diff，识别并保留用户已有修改；
- 搜索调用方、协议、依赖和受影响边界；
- 运行不会写入项目文件或改变外部状态的诊断命令。

确认前禁止写入、创建、删除、重命名或格式化项目文件，禁止应用 Patch、修改 Git 状态、安装依赖或执行可能生成受跟踪文件的命令。若调研本身需要额外权限或会改变状态，先单独请求授权，但该授权不等于批准实施计划。

## 输出计划

计划应与任务规模相称，并让用户能够判断即将授权的范围。至少说明：

1. 目标与预期行为；
2. 预计修改的文件、模块或职责边界；
3. 实施步骤和关键设计选择；
4. 测试、类型检查、构建或其他验证方式；
5. 已发现的风险、假设、用户现有修改或仍需决策的事项。

无法在修改前确定到具体文件时，可以给出模块或边界，并说明实施中如何定位。不要为了形式虚构风险、文件或步骤。

输出计划后停止，不得在同一轮开始修改。明确请求用户确认。阻断性选择尚未确定时，先请用户决定，更新计划后再请求确认。

## 确认后

“确认”“按这个计划做”“继续实施”等明确同意可视为授权。只实施已确认的范围，并按计划完成适当验证。

实现中发现需要实质性扩大范围、改变关键设计、触碰计划明确排除的文件，或需要新的外部状态变更时，停止修改，说明原因并提交更新后的计划，等待再次确认。计划范围内的局部实现细节无需重复请求确认。

若用户拒绝、要求调整或只批准部分计划，按新的边界更新计划；在获得新的明确确认前保持只读。
