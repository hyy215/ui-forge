# 按影响范围制定修改计划

在必要的只读定位后判断修改范围。计划与验证应匹配实际影响，不按文件数量机械分级。

## 局部修改

用户已要求实现、修复或调整，目标和预期行为明确，且定位确认影响局部、不涉及下述需确认事项时，简短说明修改范围和验证方式后直接实施，无需单独等待计划确认。典型情况包括文案、局部样式、普通字段校验和对应测试调整。

仅询问可行性、原因或方案不授权修改。用户明确要求“先计划”“等我确认”或本次主动调用 `$plan-before-code` 要求确认时，先提交计划并等待，不走直接执行路径。

## 需要确认的修改

以下情况先完成必要的只读调研，给出可审阅计划并等待用户明确确认：

- 改变架构、职责边界、公共通信协议、权限或审批规则、任务生命周期及恢复语义；
- 影响尚不能可靠界定，或存在决定实现方向的产品歧义；
- 用户明确要求修改前确认。

计划说明目标与预期行为、预计修改的文件或边界、关键选择、验证方式，以及确实存在的风险和已有修改。先解决阻断性选择，不为形式添加无关风险或调查。输出计划后停止，不在同一轮修改；明确请求确认。

## 调研与执行

- 先定位候选路径，读取适用约定、相关实现、直接调用方和测试；同一会话已完整读取且未变化的内容不重复读取。无关工作区修改只登记路径并保留。
- 需要确认时，确认前不写入项目文件、不改变 Git 状态、不安装依赖，也不运行会生成项目产物的命令。诊断的单独授权不等于实施计划获批。
- “确认”“按这个计划做”“继续实施”等明确同意授权计划内修改；范围内的局部实现选择不重复确认。用户只批准一部分时遵守该边界。
- 局部修改中发现上述需确认事项，或实施中需要实质扩大已确认范围、改变关键设计时，先停止相关修改并更新计划。已经获得授权的范围无需重新授权。
- 计划或局部修改授权不扩大执行权限；安装依赖、Git 交付、发布及删除用户文件仍遵守仓库的明确授权要求。
- 修改后复核本次增量及受影响接口，按根 `AGENTS.md` 运行适用验证；无新增变化或失败证据时不重复执行已通过的检查。
